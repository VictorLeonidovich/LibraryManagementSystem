## 🏛 Архитектура проекта и архитектурные особенности

Программный комплекс реализует классическую монолитную архитектуру на базе паттерна MVC (Model-View-Controller) со строгим разделением ответственности по слоям (*Package-by-Layer*). Иерархия пакетов в каталоге `src/main/java/com/kvl/library` жестко определяет границы компонентов, обеспечивая изоляцию логики и предсказуемость транзакционных границ:

* **UI-слой (Пользовательский интерфейс):** Серверный рендеринг (Server-Side Rendering — SSR) динамических страниц. Логика отображения полностью отделена от бизнес-логики.
* **API-слой (Интерфейс программирования):** Выделенный REST API для внешних интеграций. Полностью изолирован от доменных моделей с помощью промежуточных объектов передачи данных (DTO) и снабжен централизованным глобальным обработчиком исключений.
* **Бизнес-логика (Сервисный слой):** Ядро системы, реализованное в виде интерфейсов и их конкретных имплементаций, отвечающее за выполнение бизнес-правил библиотечной системы. Архитектурно поддерживает паттерн **«Стратегия»** для переключения механизмов отправки уведомлений (`sync`, `async`, `webclient`, `kafka`).
* **Данные (Доменный слой):** Набор объектно-реляционных моделей (JPA-сущностей), описывающих сущности предметной области (книги, авторы, категории, издатели). На уровне конфигураций активирована защита от неоптимальной пагинации в оперативной памяти (In-Memory Pagination) при Fetch Join операциях.

### ⚙️ Инфраструктурные особенности и профилирование сред
Архитектура приложения поддерживает сквозное разделение логики на 4 независимых профиля конфигурации (`dev`, `test`, `containers`, `prod`). При этом все чувствительные параметры, порты и учетные записи внешних систем изолированы на уровне единого файла переменных окружения (`.env`) в корне проекта. Это гарантирует гибкую подстановку настроек в целевые профили без изменения кодовой базы:
1. **Продуктивный контур (`prod`):** Конфигурация для живого сервера. Hibernate ddl-auto переведен в режим верификации соответствия (`validate`), Open Session in View (OSIV) принудительно отключен для экономии пула соединений, а детальная трассировка ошибок скрыта от конечных клиентов. Предусмотрена схема с установкой обратного прокси-сервера (Nginx) перед встроенным сервером приложений Tomcat.
2. **Контейнерная среда (`containers`):** Окружение для автоматического тестирования в изолированной сети Docker. Включает строгие лимиты пула соединений HikariCP (`maximum-pool-size=3`) во избежание перегрузки инфраструктуры.
3. **Локальная разработка (`dev`):** Окружение для быстрой локальной отладки. Включает вывод генерируемых SQL-запросов в консоль и активацию отладочных веб-панелей.
4. **Модульное тестирование (`test`):** Окружение для легковевых тестов. Запуск миграций базы данных принудительно отключается ради ускорения сборки контекста, а автоконфигурация распределенных брокеров и внешняя сеть полностью блокируются для изоляции тестов.

## 🛠 Технологический стек

Выбор технологий обусловлен требованиями к масштабируемости, безопасности и производительности, соответствующими квалификационному уровню Middle.

### 💻 Базовый серверный стек
* **Платформа и фреймворк:** Java 17 (LTS), Spring Boot 4.0.6, Spring Data JPA (Hibernate).
* **Фронтенд-компоненты:** HTML5, Thymeleaf (серверный динамический рендеринг страниц).
* **Сборка и кодогенерация:** Apache Maven, Lombok (с конфигурацией `lombok.config` для корректного подсчета покрытия), MapStruct.

### 🔒 Обеспечение безопасности и разграничение доступа
* **Подсистема безопасности:** Spring Security с автоматической инициализацией системных учетных записей администраторов и пользователей.
* **Механизм авторизации:** JSON Web Token (библиотека `jjwt-api`, бесшовная Stateless-авторизация). Секретный ключ подписи и параметры жизненного цикла токенов скрыты за переменными окружения ОС (`JWT_SECRET` и `JWT_EXPIRATION`).

### 💾 Управление данными, миграции и оптимизация производительности
* **Базы данных:** PostgreSQL (прод/контейнеры), Встроенная СУБД H2 Database (разработка/тесты в режиме совместимости `MODE=PostgreSQL`).
* **Версионирование схем данных:** Liquibase Core (детерминированное версионирование через мастер-файл `db.changelog-master.yaml` с разделением контекстов `prod` / `test`).
* **Слой кэширования:** Подсистема Spring Boot Cache, резидентная СУБД Spring Data Redis (именованный кэш `popularIsbns` с обязательной авторизацией и TTL 1 минута в prod; режим `none` в dev/test/containers).

### 🔄 Интеграционное взаимодействие, распределенный обмен сообщениями и локализация
* **Брокеры сообщений и реактивный стек:** Apache Kafka (режим кластера KRaft, образ `cp-kafka:7.5.0`, топик `email-notifications-topic`, изоляция по группам `library-notification-prod-group` / `library-notification-containers-group`), Spring WebFlux (компонент `WebClient` для неблокирующих HTTP-запросов).
* **Интернационализация (I18N):** Поддержка мультиязычности интерфейса на основе ресурсных бандлов в директории `i18n/messages` с принудительной кодировкой UTF-8 для корректного отображения кириллицы.
* **Почтовая служба:** Модуль Spring Boot Mail. Промышленный контур использует защищенный протокол SSL (порт 465) и авторизацию для интеграции с внешними серверами Google / Yandex SMTP, в то время как локальные и контейнерные среды перенаправляют почтовый трафик на SMTP-заглушку Mailhog (порты 1025/8025).

### 📊 Мониторинг, логирование и документация
* **Документирование API:** Спецификация Springdoc OpenAPI UI (Swagger) с ограничением сканирования классов пакета `com.kvl.library.controller.api`.
* **Телеметрия и метрики:** Модуль Spring Boot Actuator в связке с сервером Prometheus (интервал сбора 15с, таргет `library-app:8080`).
* **Логирование и ELK-стек:** Logback (`logback-spring.xml`) с поддержкой `RollingFileAppender` (ротация до 10MB, лимит 3GB, хранение 30 дней) для интеграции со сборщиком логов Logstash (пайплайн с dissect-фильтром в `logstash.conf`), Elasticsearch и Kibana.

### 🐳 Локальная оркестрация и инфраструктура разработки
* **Среда развертывания (11 контейнеров):** Управление через `docker-compose.yml`, объединяющий в единую изолированную сеть приложение (`library-app` на базе `eclipse-temurin:17-jre-alpine` с G1GC и non-root пользователем), PostgreSQL (`pg_isready`), Redis (`requirepass`), Kafka (KRaft), Mailhog, Prometheus, Grafana, SonarQube (порт 9000 для контроля качества), Elasticsearch, Logstash и Kibana.

### 🚀 Автоматизация CI/CD и контроль качества
* **Инфраструктура сборки:** Автоматический пайплайн GitHub Actions (*Java CI/CD Pipeline with Testcontainers* с выделенными правами `security-events: write`).
* **Контейнеризация тестов:** Технология Testcontainers, обеспечивающая автоматический изолированный запуск реальной СУБД PostgreSQL в Docker-контейнерах в рамках шагов сборки в CI/CD.
* **Анализ безопасности и покрытия:** Статический анализ GitHub CodeQL v4, OWASP Dependency Check и плагин JaCoCo (жесткий блокирующий порог сборки < 70% на основе суммарных CSV-отчетов).

В цепочку реактивного POST-запроса внедрен обязательный заголовок `X-Internal-Token`, динамически считывающий секретный ключ из конфигурации среды. Межсервисный вызов успешно проходит проверку подлинности в фоновом потоке без блокирования UI-интерфейса.

  * Это упростило масштабирование кодовой базы, изолировало JWT-логику от веб-интерфейса и исключило накладные расходы на обработку токенов при загрузке статических ресурсов.

### 🟢 Сценарий 1: Тестирование защищенных эндпоинтов в Swagger UI

### 🟠 Сценарий 2: Тестирование REST API через Postman

Для отправки запросов через Postman к защищенным эндпоинтам необходимо предварительно получить JWT-токен и передавать его в каждом последующем запросе в HTTP-заголовке `Authorization: Bearer <ваш_токен>`.

#### 1. Аутентификация и получение JWT-токена (Открытый эндпоинт)
* **Метод и URL:** `POST http://localhost:8080/api/auth/login` *(или IP-адрес целевого сервера, например `http://10.16.113.123:8080/api/auth/login`)*
* **Тело запроса (Body -> raw -> JSON):**
```json
{
    "username": "admin",
    "password": "password"
}
```
* **Действие:** Отправьте запрос и скопируйте строку `token` из тела ответа. В Postman для следующих запросов перейдите на вкладку **Authorization**, выберите тип **Bearer Token** и вставьте скопированное значение.

#### 2. Получение списка авторов с пагинацией и сортировкой (Защищенный эндпоинт)
* **Метод и URL:** `GET http://localhost:8080/api/v1/authors?page=0&size=5&sort=name,desc`
* **Параметры (Params):**
  * `page` = `0` (индекс запрашиваемой страницы)
  * `size` = `5` (количество элементов на странице)
  * `sort` = `name,desc` (сортировка по имени в обратном порядке)

#### 3. Создание новой сущности автора (Защищенный эндпоинт)
* **Метод и URL:** `POST http://localhost:8080/api/v1/authors`
* **Тело запроса (Body -> raw -> JSON):**
```json
{
  "name": "Фёдор Достоевский",
  "description": "Великий русский писатель, классик мировой литературы и один из самых читаемых авторов в мире."
}
```

#### 4. Удаление автора по уникальному идентификатору (Защищенный эндпоинт)
* **Метод и URL:** `DELETE http://localhost:8080/api/v1/authors/3`
* **Действие:** Данная операция удаляет из базы данных сущность автора с `id = 3`.

## 🚀 Инструкция по запуску инфраструктуры

Управление контейнерами разделено на два сценария: локальная разработка (запуск изолированной СУБД для профиля `prod`) и полноценное развертывание всего стека (11 контейнеров) через Docker Compose.

### 🍃 Сценарий 1: Запуск изолированной СУБД для локальной разработки (Prod)

Если приложение запускается локально из IDE под профилем `prod`, необходим запуск только СУБД PostgreSQL.

* **Первичный запуск контейнера базы данных:**
```bash
docker run --name library-postgres -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=root -e POSTGRES_DB=library_db -p 5432:5432 -d postgres:latest
```
* **Детализация параметров:**
  * `--name library-postgres` — присваивает контейнеру уникальное системное имя;
  * `-e POSTGRES_USER=postgres` — задает имя главного администратора базы данных;
  * `-e POSTGRES_PASSWORD=root` — устанавливает пароль суперпользователя;
  * `-e POSTGRES_DB=library_db` — автоматически инициализирует целевую пустую схему данных для библиотеки;
  * `-p 5432:5432` — транслирует стандартный сетевой порт из контейнера на хост-машину для связи со Spring Boot;
  * `-d postgres:latest` — загружает актуальный официальный образ СУБД и выполняет запуск в фоновом режиме (detached).

* **Принудительный перезапуск СУБД (с очисткой старого контейнера):**
```bash
docker rm -f library-postgres
docker run --name library-postgres -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=root -e POSTGRES_DB=library_db -p 5432:5432 -d postgres:latest
```

## 📊 Мониторинг, метрики и логирование (Observability)

В проект встроена полноценная production-ready система мониторинга на базе **Spring Boot Actuator**, **Micrometer**, **Prometheus** и **Grafana** для отслеживания производительности JVM, потребления памяти и пропускной способности HTTP-запросов в реальном времени.

Базовая точка входа для проверки метрик приложения:
👉 **http://localhost:8080/actuator**

Поведение системы и доступ к метрикам настроены в зависимости от активного профиля:

### 🛠️ В профиле разработки (dev):
Доступны **все** встроенные эндпоинты управления (`management.endpoints.web.exposure.include=*`).
* **`/actuator/health`** — показывает полную информацию о состоянии системы и детальный статус подключения к БД H2 (`show-details=always`).
* **`/actuator/prometheus`** — генерирует системные метрики приложения в текстовом формате, оптимизированном для сборщика Prometheus.
* **`/actuator/loggers`** — позволяет просматривать и динамически изменять уровни логирования классов прямо на лету без перезапуска приложения.

### 🚀 В продакшн профиле (prod):
В целях безопасности доступ к инфраструктуре строго ограничен (`management.endpoints.web.exposure.include=health,info,prometheus`), а цепочка фильтров Spring Security разрешает сбор данных только для доверенных внутренних сервисов.
* Открыты только эндпоинты **`/actuator/health`**, **`/actuator/info`** и **`/actuator/prometheus`**.
* Отображение внутренней структуры и деталей подключения к PostgreSQL полностью скрыто (`show-details=never`) для предотвращения утечки данных об архитектуре сервера.
* Автоматический замер времени выполнения HTTP-запросов (HTTP Latency & RPS) включен по умолчанию средствами встроенного Micrometer.

### 📈 Инфраструктура мониторинга (Docker-окружение)
Полный стек мониторинга разворачивается автоматически в изолированной Docker-сети через `docker-compose.yml`:

1. **Prometheus (`port 9090`)** — каждые 15 секунд опрашивает эндпоинт приложения `/actuator/prometheus`, агрегирует и сохраняет метрики во временную базу данных (TSDB).
  * Веб-интерфейс: **http://localhost:9090** (Статус сборщика: *Status -> Targets*)
2. **Grafana (`port 3000`)** — визуализирует собранные данные Prometheus на интерактивных панелях. В систему интегрирован кастомный дашборд для мониторинга:
  * **JVM Memory (Heap/Non-Heap)** — загрузка и очистка памяти сборщиком мусора (GC).
  * **JVM Threads & CPU** — активность потоков и нагрузка на процессор в моменты пиковой работы.
  * **HTTP Requests (RPS)** — пропускная способность эндпоинтов бизнес-логики с фильтрацией по методам и HTTP-статусам ответов.
  * Веб-интерфейс: **http://localhost:3000** (Логин/Пароль по умолчанию: `admin` / `admin`). Данные и дашборды сохраняются между перезапусками контейнеров благодаря именованному volume `grafanadata`.

## 📝 Централизованное логирование (ELK Stack)
Для агрегации, структурированного анализа и быстрого поиска по логам всего приложения в production-профиле развернута классическая связка **Elasticsearch**, **Logstash** и **Kibana** (версия `8.12.2`).

### 🔄 Пайплайн доставки и обработки логов (File-based):
1. **Spring Boot App** записывает структурированные логи в файл `library-prod.log` внутри изолированного Docker-volume (`applogs`) с использованием строгого разделителя `|` для полей.
2. **Logstash** монтирует этот же volume, в реальном времени считывает новые строки, разбирает их с помощью плагина `dissect` на атомарные JSON-поля и отправляет в индексатор.
3. **Elasticsearch** индексирует входящие данные для мгновенного полнотекстового поиска.
4. **Kibana** предоставляет веб-интерфейс для глубокой аналитики.

### 📈 Инфраструктура ELK (Docker-окружение)
Все компоненты настроены в ресурсосберегающем режиме (`ES_JAVA_OPTS` / `LS_JAVA_OPTS`) специально для локальных сред разработки:

* **Elasticsearch (`port 9200`)** — база данных и поисковый движок.
  * Проверка статуса: **http://localhost:9200**
* **Logstash** — сервер конвейера обработки данных. Автоматически группирует логи по индексам `library-app-logs-YYYY.MM.dd`.
* **Kibana (`port 5601`)** — аналитическая визуальная панель.
  * Веб-интерфейс: **http://localhost:5601**
  * Для просмотра логов бизнес-логики перейдите в **Analytics -> Discover**, настройте Data View для индекса `library-app-logs-*` и используйте фильтр KQL (Kibana Query Language): `logger.keyword : c.k.l.*"`

  * **Отказоустойчивость и автономность:** Все вызовы обернуты в безопасные блоки обработки исключений, что гарантирует 100% работоспособность приложения и интеграционных тестов даже при временной недоступности сервера Redis.

## 🛠️ Экспорт данных и отчетность. Интеграция почтового сервиса.

### Реализованная архитектура и стек технологий модуля:
* **Архитектурный паттерн «Стратегия» (Strategy Pattern):** Логика генерации документов полностью изолирована через интерфейс `BookExportService` и динамическую фабрику `BookExportFactory`, что позволяет добавлять новые форматы (например, CSV) без изменения существующего кода контроллеров.
* **Интерактивный Web UI (Thymeleaf + JS):** На страницу просмотра книги добавлен адаптивный блок управления отчетностью. Текст и иконка кнопки динамически меняются без перезагрузки страницы («Сохранить» для локального скачивания файлов / «Отправить» при выборе отправки на Email с валидацией поля ввода).
* **Генерация Excel (XLSX):** Реализована на базе **Apache POI**. Документ формируется в виде аккуратной карточки книги с применением стилей оформления (жирные шрифты заголовков, цветовое выделение шапки, тонкие границы ячеек и автоматический перенос длинного текста описания).
* **Генерация PDF:** Реализована на базе **OpenPDF** с полной поддержкой кириллицы. Реализован механизм динамического поиска и ленивой загрузки системных TrueType шрифтов (`Arial` / `DejaVuSans`) для корректного рендеринга русского текста как на локальной машине разработчика, так и внутри изолированного Docker-контейнера.
* **Модуль Почты (Spring Boot Starter Mail):** Создан надежный сервис `EmailServiceImpl` на базе `JavaMailSender` для отправки писем с поддержкой вложений в формате Multipart. Проведена интеграция со спецификацией Jakarta Mail.
* **Безопасность (Spring Security):** Настройки `SecurityConfig` скорректированы с сохранением строгой политики защиты сессий (Stateless) — эндпоинт экспорта отчетов `/books/*/export` безопасно добавлен в исключения CSRF-фильтрации для корректной обработки POST-форм.
* **Многопрофильная конфигурация инфраструктуры:** Настройки почтового клиента гибко разделены по целевым окружениям (`dev` / `test` / `prod` / `containers`). В файл `.env` и `docker-compose.yml` вынесены переменные среды, защищающие учетные данные на продакшене. Локальное тестирование и отладка писем в докере развернуты через почтовую заглушку **Mailhog** с веб-интерфейсом.

### 🌐 Инструкция по использованию MessageSource (i18n) в Java-коде

После инициализации конфигурации `InternationalizationConfig`, текстовые сообщения из файлов ресурсов `messages.properties` должны внедряться в логику приложения через интерфейс `MessageSource`.

#### 1. Использование в бизнес-логике / Обработчиках ошибок

Для динамического получения перевода с учетом текущей локали пользователя используется статический контекст `LocaleContextHolder.getLocale()`. Внедрение `MessageSource` выполняется строго через конструктор.

```java

...
@RestControllerAdvice
public class ApiGlobalExceptionHandler {

    private final MessageSource messageSource;

    public ApiGlobalExceptionHandler(final MessageSource messageSource) {
        this.messageSource = messageSource;
    }

    /**
     * Пример получения мультиязычного сообщения по его ключу.
     */
    private String getErrorMessage(final String messageKey) {
        return messageSource.getMessage(messageKey, null, LocaleContextHolder.getLocale());
    }
}
```

#### 2. Использование в интеграционных тестах (MockMvc)

В тестах `MessageSource` внедряется через аннотацию `@Autowired`. Локаль (`Locale.ENGLISH` или `Locale.of("ru")`) передается в метод принудительно для верификации конкретного языкового пакета.

```java

...
class AuthorRestControllerTest {
    
    ...

    @Autowired
    private MessageSource messageSource;

    @Test
    void shouldReturnLocalizedValidationError() throws Exception {
        // Извлекаем ожидаемую строку перевода для английской локали
        final String expectedMessage = messageSource.getMessage("error.validation.failed", null, Locale.ENGLISH);

        mockMvc.perform(get("/api/authors/invalid-id")
                        .header("Accept-Language", "en")) // Передаем заголовок локали
                .andExpect(status().isBadRequest())
                .andExpect(jsonPath("\$.message").value(expectedMessage));
    }
}
```

## 📧 Распределенная система отправки уведомлений и отчетов

### 🏛 Архитектурная схема взаимодействия

```aiignore
  [Бизнес-логика] 
         │
         ▼
[NotificationDispatcher] (Интерфейс-Фасад)
         │
         ├─► (sync) ──────► [EmailServiceImpl] ──► (Шлет реальный Email)
         │
         ├─► (async) ─────► [@Async Поток] ─────► [EmailServiceImpl] ──► (Шлет реальный Email)
         │
         ├─► (webclient) ─► [WebClient] ──(HTTP)──► [@RestController (Локальный эндпоинт)] ──► [EmailServiceImpl]
         │
         └─► (kafka) ─────► [KafkaTemplate] ──(Брокер)──► [@KafkaListener (Локальный консьюмер)] ──► [EmailServiceImpl]
```

### ⚙️ Конфигурация переключения режимов (`application.properties`)

```properties
notification.strategy: kafka # Доступные варианты: sync, async, webclient, kafka
```

### 🛠 Описание реализуемых стратегий

1. **`sync` (Синхронная передача данных):**
* **Технология:** Прямой блокирующий вызов Core-сервиса.
* **Суть:** Поток веб-запроса блокируется до тех пор, пока почтовый сервер полностью не примет тяжелое вложение. Используется для демонстрации классического "узкого горлышка" (UI замерзает на время отправки).

2. **`async` (Асинхронность через `@Async` и `CompletableFuture`):**
* **Технология:** Пул потоков Spring (`ThreadPoolTaskExecutor`) + `CompletableFuture.runAsync()`.
* **Суть:** Фоновая обработка задачи. Пользователь мгновенно получает ответ на UI ("Отчет отправляется"), в то время как отправка письма происходит в параллельном потоке приложения.

3. **`webclient` (Межсервисное взаимодействие / Loopback REST):**
* **Технология:** Реактивный неблокирующий `WebClient` (Spring WebFlux) + локальный `@RestController`.
* **Суть:** Имитация микросервисной архитектуры внутри монолита. `WebClient` отправляет асинхронный HTTP POST-запрос с `Multipart` данными (DTO и массив байт вложения) на внутренний служебный эндпоинт, который затем делегирует отправку почтовому сервису.

4. **`kafka` (Событийно-ориентированная архитектура / EDA):**
* **Технология:** `KafkaTemplate` + `@KafkaListener` (Spring Kafka в Docker-контейнере KRaft).
* **Суть:** Очередь сообщений. Задаче на отправку присваивается уникальный JSON-формат, после чего она публикуется в топик `email-notifications-topic`. Автономный листенер асинхронно вычитывает сообщения из брокера и гарантирует доставку писем даже при высоких пиковых нагрузках.

### 📊 Результаты бенчмаркинга и сравнительный анализ стратегий

Для оценки эффективности распределенной обработки тяжелых задач (генерация PDF-отчетов и сетевая отправка через TLS Google SMTP шлюз на порту 465) был проведен ряд архитектурных замеров с использованием встроенного инструментария `org.springframework.util.StopWatch`.

Ниже представлены реальные метрики времени блокировки основного потока веб-сервера (`UI Thread Latency`) для каждой из четырех реализованных стратегий:

| Режим работы (Strategy Type) | Время блокировки UI потока | Механизм изоляции потоков | Готовность к микросервисной архитектуре |
| :--- | :--- | :--- | :--- |
| 🔴 **Синхронный (`sync`)** | **2812 мс** | Отсутствует (Блокирующий вызов) | Непригодно (Критическое узкое горлышко) |
| 🟡 **Реактивный (`webclient`)** | **160 мс** | Сетевой (HTTP REST Loopback) | **Высокая** (Готовый сетевой контракт RPC) |
| 🟢 **Брокер сообщений (`kafka`)** | **291 мс** | Полный (Событийная шина EDA) | **Эталонный Enterprise-стандарт** |
| 🔵 **Асинхронный (`async`)** | **5 мс** | Локальный (Фоновый пул JVM) | Ограниченная (Внутренняя оптимизация монолита) |

### 🔍 Архитектурный разбор логов выполнения (Deep Dive)

#### 1. Синхронный режим (`sync`) — 2812 мс
*   **Логика:** Поток веб-запроса `[nio-8080-exec-*]` полностью замирает почти на 3 секунды, дожидаясь завершения TCP/SSL рукопожатия с серверами Google.
*   **Проблема:** При пиковой нагрузке пул потоков веб-сервера Tomcat мгновенно исчерпывается, что приводит к зависанию всего интерфейса библиотеки для остальных пользователей (`Thread Starvation`).

#### 2. Асинхронный режим (`async`) — 5 мс
*   **Логика:** Самый быстрый показатель времени отклика веб-потока. Аннотация `@Async` в связке с `CompletableFuture.runAsync()` мгновенно делегирует тяжелую задачу в параллельный пул потоков приложения (`Spring Task Execution`).
*   **Плюс:** Пользователь получает мгновенный отклик на UI, пока фоновый поток изолированно шлет письмо. Оптимально для локальной оптимизации монолита.

#### 3. Реактивный режим (`webclient`) — 160 мс
*   **Логика:** Имитация межсервисного обмена. Неблокирующий `WebClient` упаковывает массив байт отчета в Multipart-форму и асинхронно шлет HTTP POST-запрос на скрытый внутренний контроллер `/api/v1/internal/notifications/email`.
*   **Плюс:** Поток UI освобождается за 160 мс (время уходит на сериализацию файла и локальное сетевое рукопожатие). Готовый шаблон для выноса логики в отдельный микросервис уведомлений.

#### 4. Брокер сообщений (`kafka`) — 291 мс
*   **Логика:** Полноценная событийно-ориентированная архитектура (EDA). Идемпотентный продюсер под управлением **Kafka 4.1.2** публикует JSON-сообщение в топик брокера за 291 мс. В эту же секунду автономный фоновый поток консьюмера `[ntainer#0-0-C-1]` вычитывает сообщение из топика и передает его в почтовый сервис.
*   **Плюс:** Гарантия 100% доставки сообщений. Даже если почтовый шлюз уйдет в офлайн на несколько минут, брокер сохранит сообщения в логе, и система обработает их автоматически сразу после восстановления сети, не потеряв ни одного отчета читателей.
